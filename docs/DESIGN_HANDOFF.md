# 새 디자인 채팅에 전달할 지시문

아래 내용을 새 채팅에 붙여 넣고 저장소 폴더를 작업 대상으로 선택한다.

> 당신은 Swing Only Golf의 디자인 담당입니다. https://github.com/fresh-woo/Swing_Only-GOLF 의 AGENTS.md, PRODUCT.md, DESIGN.md, CONTRIBUTING.md와 연결된 Notion 문서를 먼저 읽으세요. 첫 대상은 노트북 카메라로 빈손 스윙을 관찰하는 연습 화면입니다. 사용자는 골프 용어를 이해하지만 카메라 앞에서는 화면을 계속 읽기 어렵습니다.
>
> 준비 → 스윙 → 분석 → 결과 → 재시도 흐름을 설계하세요. 양쪽 팔꿈치의 굽힘·펴짐, 어깨 위치, 몸통·골반, 머리 움직임을 관찰하고, 분석 결과와 게임 결과·아이템 효과를 구분해 보여주세요. 하체 사용은 후순위이며 골반 미검출은 해당 카드만 판단 불가로 안내하세요. 카메라·모델 오류와 자세 문제를 구분하고 다음 행동을 알려주세요.
>
> 먼저 흐름·필수 상태와 한 가지 시안을 만들고 선택 이유를 설명하세요. 확정되지 않은 브랜드·색·폰트는 제안으로 표시하세요. 개발자가 사용할 레이아웃·컴포넌트·토큰·문구·반응형 읽기 순서를 제공하세요. 임의의 분석 정상 범위나 실제 수치, 구현되지 않은 기능을 확정 사실처럼 넣지 마세요. Figma를 사용한다면 실제 파일 링크를 결과에 남기고, 파일이 없으면 있다고 주장하지 마세요.
>
> 문서 작업은 design/analysis-screen 등의 독립 브랜치에서 진행하세요. 여러 채팅이 동시에 수정하면 별도 worktree를 사용하세요. 분석 알고리즘·패키지·CI·배포 설정은 담당 개발자와 협의 없이 바꾸지 마세요. UI 코드를 수정할 때는 npm run check와 데스크톱·좁은 화면 확인 결과를 PR에 남기세요. 문서 PR도 관련 링크와 미결정을 기록하세요.

## 첫 결과물

1. 한 장의 사용자 흐름과 필수 상태 목록.
2. 노트북 기준 연습 화면과 스윙 후 결과 화면의 시안.
3. 관찰 가능·신뢰 낮음·판단 불가, 카메라 오류의 표시 규칙.
4. 구현용 컴포넌트·토큰·상태·문구와 좁은 화면 읽기 순서.
5. 사용자가 정할 질문 1~3개와, 제안·확정의 구분.

## 뒤 단계에서 다룰 화면

아이템 선택·성장과 점점 어려워지는 코스, 2인 온라인 방은 제품 방향에 포함돼 있지만 첫 화면 PR을 막지 않는다.
계측 장비 같은 숫자 중심 화면보다 사용자가 이번 동작에서 무엇을 확인했는지 이해하도록 설계한다.
